# 邀请流程与用户体验分析

## 原则：用户不感知「被邀请」

- **被分享进入的用户**（点击分享链接的人）不应在界面上看到「被邀请」「通过 XX 邀请」等文案，不强调其「被邀请人」身份。
- 流程与正常进入一致：例如仅展示「加入组织」「输入邀请码」等中性操作，不展示邀请人昵称、不 toast「已通过邀请码绑定」等会让用户意识到「被绑定」的提示；分销绑定在后台静默完成即可。

---

## 一、两种邀请模式概览

| 维度 | 群组邀请 | 分销邀请 |
|------|----------|----------|
| **入口** | 群组详情页 → 分享给好友/朋友圈 | 个人中心「我的邀请」→ 分享给好友 |
| **分享参数** | `inviteCode`(群组码) + `inviterOpenid` + `ref`(可选，用户邀请码) | `inviteCode`(用户邀请码) |
| **落地页** | 组织页 `/pages/group/group` | 首页 `/pages/index/index` |
| **业务目标** | 新用户加入指定组织 | 新用户与邀请人绑定上下级关系，获得积分/奖励 |

### 分销绑定规则（已实现）

- **仅新用户可算为下级**：若用户**之前已登录过**（即 users 表中该账号的 `createTime` 早于当前时间超过约 15 分钟），则不再执行绑定、不发放邀请奖励、不记为邀请人的下级。云函数 `referral.bindInvite` 会返回 `alreadyRegistered: true`；前端**不向用户展示**「仅新用户可通过邀请码绑定」等提示，静默清除 pending 即可（用户不感知被邀请）。

---

## 二、群组邀请流程

### 2.1 流程简述

1. **邀请人**：在群组详情页点击分享 → 生成链接 `/pages/group/group?inviteCode=群组码&inviterOpenid=xxx&ref=我的邀请码`。
2. **被邀请人点击链接**：直接打开**组织页**；`app.onLaunch` 将 `inviteCode`、`inviterOpenid` 写入 `pendingGroupInviteCode` / `pendingGroupInviterOpenid`，若有 `ref` 则写入 `pendingInviteCode`。
3. **已登录用户**：组织页 `checkInviteCodeFromShare()` 从当前页 `options` 读取 `inviteCode` / `inviterOpenid`，自动弹出「加入组织」弹窗，邀请码已预填，点击「加入」即可。
4. **未登录用户**：组织页因无 `openid` 不弹窗，仅显示「登录后可创建或加入组织」；用户去首页登录 → 登录成功后 `index` 的 `onConfirmAuth` 从 storage 读取 `pendingGroup*`，设置 `shouldOpenJoinModal` 并 `switchTab` 到组织页 → 组织页 `tryApplyJoinModal()` 弹出加入弹窗。
5. **加入成功**：`joinByInviteCode` 写入成员关系，若有 `inviterOpenid` 会更新邀请人「邀请好友」任务与成就；然后 `switchTab` 回首页。

### 2.2 体验优点

- 落地页即组织页，与「加入组织」强相关，心智清晰。
- 已登录用户：邀请码预填，一步点击「加入」即可，路径短。
- 分享标题带组织名和邀请码，便于在聊天里口头核对。

### 2.3 体验问题与优化建议

| 问题 | 说明 | 建议（遵守「用户不感知被邀请」） |
|------|------|--------------------------------|
| **未登录时无引导** | 从群组链接进来的未登录用户，首屏只有「登录后可创建或加入组织」。 | 若需引导，使用中性文案如「登录后可加入组织」或「登录后使用」，**不**展示「您有一则组织邀请」「有人邀请你」等让用户感知被邀请的表述。 |
| **加入弹窗** | 弹窗只有「输入邀请码」，可考虑展示组织名。 | 若展示组织名，仅「加入 XXX 组织」即可；**不**展示「邀请人：XXX」，避免用户感知到被邀请。 |
| **取消即永久不再提示** | 用户点「取消」会调用 `addDismissedJoinCode(code)`，该邀请码之后不再自动弹窗。 | 可改为「本次忽略」与「不再提示」两种选项，或仅在「不再提示」时写入 dismissed。 |
| **参数命名易混** | 群组分享与分销分享都用 `inviteCode`（一为群组码，一为用户码），仅靠是否有 `inviterOpenid` 区分。 | 文档中明确约定；若后续扩展，可考虑群组用 `groupInviteCode` 等区分。 |

## 三、分销邀请流程

### 3.1 流程简述

1. **邀请人**：在「我的邀请」页分享 → 链接为 `/pages/index/index?inviteCode=用户邀请码`（此处 `inviteCode` 实为 ref）。
2. **被邀请人点击**：打开**首页**；`app.onLaunch` 将 `query.inviteCode` 存为 `pendingInviteCode`。
3. **登录后**：首页 `init()` / `onConfirmAuth()` 中调用 `tryBindInviteCode(openid)`，用 `pendingInviteCode` 调云函数 `referral.bindInvite`。仅当该用户为**新用户**（账号创建时间在 15 分钟内）时才绑定并发积分；若为老用户则返回 `alreadyRegistered`，不绑定、不算下级。**用户不感知被邀请**：不向被分享进入的用户展示「已通过邀请码绑定」「仅新用户可通过邀请码绑定」等 toast，绑定静默完成。
4. **已登录用户**从分销链接进入：同样在 `init()` 里 `tryBindInviteCode`；因账号早已存在，云函数判定为已注册用户，不绑定；无任何邀请相关提示。

### 3.2 体验优点

- 绑定逻辑集中在一处，登录后自动处理，无需额外步骤；用户侧无「被邀请」感知，与正常进入一致。
- 与群组邀请共用一套「先存 pending，登录后处理」的模式，逻辑一致。

### 3.3 体验问题与优化建议（用户不感知被邀请）

| 问题 | 说明 | 建议 |
|------|------|------|
| **不展示邀请相关文案** | 被分享进入的用户不应看到「通过 XX 邀请」「被邀请」等。 | **不**在首页/登录区展示「通过好友邀请加入」「好友邀请你一起来打卡」等；不展示「已通过邀请码绑定」「已与邀请人建立关系」等 toast。绑定成功静默处理即可；邀请人侧反馈可依赖「我的邀请」页数据。 |
| **未登录时** | 未登录用户看到的是通用授权区。 | 保持通用授权文案即可，**不**增加「邀请」「绑定」相关引导，避免用户感知被邀请。 |
| **分享参数与群组共用 inviteCode** | 分销分享用 `inviteCode` 传用户邀请码，群组用 `inviteCode` 传群组码；当前用 `ref`/`inviterOpenid` 区分，但命名不直观。 | 分销分享可改为统一使用 `ref` 传用户邀请码（与群组分享中的 ref 一致），避免与群组 `inviteCode` 混淆。 |

## 四、两种邀请的交叉场景（群组链接带 ref）

- 群组分享若带上 `ref`（邀请人的用户邀请码），则：
  - `pendingInviteCode = ref`（正确，用于 bindInvite）；
  - `pendingGroupInviteCode` / `pendingGroupInviterOpenid` 仍为群组邀请相关。
- 登录后：先执行 `tryBindInviteCode(ref)` 绑定上下级，再在组织页弹加入弹窗；顺序合理。
- **潜在问题**：若群组分享未带 `ref`（例如邀请人尚未生成用户邀请码），当前逻辑会走 `else if (query.inviteCode)`，把**群组码**写入 `pendingInviteCode`；登录后 `bindInvite(群组码)` 会在 users 表查不到该邀请码而失败，仅多一次无效请求，不影响加入组织。建议在 `app.onLaunch` 中：**仅当不存在群组邀请（无 `inviterOpenid`）时，才用 `query.inviteCode` 作为 `pendingInviteCode`**，避免把群组码误当用户邀请码。

---

## 五、建议的代码级修改（简要）

1. **app.ts**  
   - 仅在「非群组邀请」时把 `query.inviteCode` 当作 `pendingInviteCode`，例如：
   - `if (query.ref) { set pendingInviteCode = ref } else if (query.inviteCode && !query.inviterOpenid) { set pendingInviteCode = inviteCode }`
2. **组织页（group）**  
   - 未登录且 storage 有 `pendingGroupInviteCode` 时，如需引导仅用中性文案（如「登录后可加入组织」），**不**使用「您有一则组织邀请」等。
   - 加入弹窗可展示组织名「加入 XXX 组织」，**不**展示邀请人信息；取消时区分「本次忽略」与「不再提示」。
3. **首页（index）**  
   - **不**向用户展示「通过好友邀请」等文案；`bindInvite` 成功或 `alreadyRegistered` 时均**不** toast 邀请相关提示，静默清除 `pendingInviteCode`，使用户无被邀请感知。

---

## 六、总结

- **原则**：被分享进入的用户不感知「被邀请」—— 不展示邀请人、不展示「已通过邀请码绑定」等提示，流程与正常进入一致。
- **群组邀请**：路径清晰、已登录体验好；弹窗与引导使用中性表述，不强调「被邀请」。
- **分销邀请**：绑定在后台静默完成，不 toast 绑定结果或「仅新用户可绑定」等，分享参数建议与群组区分（如统一用 `ref` 表示用户邀请码）。
- **交叉逻辑**：通过「仅当非群组邀请时用 inviteCode 作 pendingInviteCode」可避免群组码被误用于 bindInvite，并保持两种邀请并存时行为一致、易维护。
